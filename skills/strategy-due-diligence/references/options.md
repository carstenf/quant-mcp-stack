# Options adapter (Option Omega + TradeBlocks)

Read the core [SKILL.md](../SKILL.md) first. This file holds sections 1 and 3-6 for options strategies (SPX and other underlyings Option Omega supports): a vendor's rules or shared Option Omega backtest, a trade log, alerts, or broker statements.

**Status: calibrated once on synthetic cases (2026-11-08, section 7); both cases were rejected after the fixes recorded there.** Not yet used on a real case: name the first real report "first real use of the options adapter" on page 1.

## Tools (golden rule, options)
- Replication and parameter neighbourhood = **Option Omega MCP** (`get_saved_backtest`, `run_backtest`, `run_optimizer`, `get_backtest_results`, `get_trade_log`). Scratch runs only: never call `save_*`, `replace_*` or `edit_*` on the user's or vendor's backtests unless the user's own capture tool says so.
- Trade-log capture = **oo-capture** from `tradeblocks-skills` (run-bound, verified to the cent against Option Omega's headline), or the user's own bulk-pull tool if they have one (for logs larger than a few hundred trades). Never page large trade logs through the model by hand.
- Statistics, robustness, risk, fills = **TradeBlocks MCP** (tools named below). Selection tests = the TradeBlocks skills **`is-this-optimum-real`** (optimizer winner vs. plateau centre) and, if installed, **`is-this-filter-real`** (entry/skip filters such as VIX or gap rules). Call them; do not re-implement their steps here.
- PSR, DSR, expected max Sharpe, MinTRL and bootstrap confidence intervals on the daily return series = **ml4t-diagnostic** (via the ML4T MCP `run_python`), the same functions as the equities adapter, so both asset classes are judged by one hurdle.
- Own code ONLY for: the rule-implied trading calendar (data checks), capital normalisation of daily P&L, charts, the report.

## Requirements
- Option Omega MCP and TradeBlocks MCP connected; TradeBlocks must read the capture folder. ML4T MCP for ml4t-diagnostic. Option quotes for fill checks in TradeBlocks (`fetch_quotes` / `get_option_snapshot`; coverage per underlying via `list_underlyings`).
- If a server is missing: stop and say which one.

## Intake additions (options)
- **Exact rules** as the vendor states them: underlying, structure and legs (delta or offset, DTE, width, quantity), entry time(s) and entry conditions/filters, exits (profit target, stop type and value, intra-minute monitoring, time exit), position sizing, days traded. Unknown fields are vendor degrees of freedom: list them.
- **Fill assumption** of the record: real fills, mid, natural, or Option Omega slippage settings; commissions per contract.
- **Capital basis**: starting capital, buying-power/margin per trade, compounding or fixed contracts. Fix it before any metric: Sharpe of daily P&L at fixed size does not depend on it, CAGR and drawdown do. State the basis next to every return figure.
- **Benchmark**: the naive mechanical version of the same structure in Option Omega (same underlying, DTE, delta, entry time, no filters, no stop optimisation), plus buy-and-hold of the underlying for context. The naive version is the "universe baseline" of the equities adapter: it separates "short premium paid" from selection skill.
- **Costs**: baseline = the record's own assumption checked against quotes; cost grid = Option Omega slippage per contract at 0 / baseline / conservative (e.g. 2x baseline) and commissions as set by the user's broker.

## 1. Input and data
- **Option Omega backtest or rules** -> reproduce the vendor's base backtest exactly (read it with `get_saved_backtest` if shared), run it, capture and verify the trade log, import into TradeBlocks (tradelog + daily log). Compare trade count, net P/L and date range with the vendor's figures; any gap is finding #1.
- **Trade log** (CSV, broker statement) -> import into TradeBlocks as its own block (`import_csv`, `plBasis` as stated). If the rules are known, also replicate in Option Omega and keep both blocks.
- **Alerts** (time-stamped messages) -> one row per alert (time, legs, stated fill); store the raw alerts with timestamps (core: incubation ledger) before any analysis.
- **Data checks (own code, `data_checks.json`)**: build the rule-implied calendar (every day the rules say a trade should exist, e.g. every trading day for a daily 0DTE strategy) and list: missing trade days (and the replicated P&L on those days - missing bad days are the options form of removed weeks), duplicate trades, trades on non-trading days or outside the stated entry window, quantity changes, fills outside the day's bid/ask, gaps around known stress days, and **stated vs. actual DTE/strikes** (e.g. a "7 DTE" rule that silently opens the next available expiry when the stated one did not exist - in 2016 Option Omega opened 54 of 302 Monday trades at 8-18 DTE because only Friday weeklies existed).
- **Holdout**: due diligence is not covered by the user's options holdout rule (core, house rules); log every run in the user's protocol. If the strategy is later rebuilt as an own one (core section 8, path 1), research may use only the research blocks of the user's options holdout scheme.

## 3. Replication, neighbourhood and fills
- **Base replication**: as section 1. Use the record's fill assumption and the baseline cost; add runs on the cost grid (sensitivity, not candidates).
- **Fill audit**: for a random sample of at least 30 vendor trades (all trades if fewer) plus every trade on the 10 worst days, replay against historical quotes (`replay_trade`, `fetch_quotes`); report the share of fills inside the bid/ask, the average fill vs. mid and vs. natural, and the P&L at natural fills. With a vendor log next to a replication: `compare_backtest_to_actual`, `analyze_discrepancies`, `analyze_live_alignment`, `analyze_slippage_trends`. Systematic advantages of the vendor exactly on bad days indicate filtering or edited fills.
- **Parameter neighbourhood (replaces the entry-delay test)**: run the TradeBlocks skill `is-this-optimum-real` on an Option Omega optimizer grid around the vendor's stated values - entry time (e.g. +-15/30/60 min), short-leg delta (+-5), DTE, stop and target level, one or two axes at a time. Its plateau centre vs. the vendor's setting answers "did the vendor publish a spike?". Count the grid cells as vendor-trial evidence (core section 2, item 3): a vendor setting that is the best of N cells needs the hurdle for at least N trials.
- **Entry filters** in the vendor's rules (VIX, gap, day of week, event days): run `is-this-filter-real` per filter if installed; otherwise at least compare filtered vs. unfiltered replication with the core plateau rule and the paired test, and say that the selection-adjusted permutation was not run.
- **Traded rule**: if one setting was recorded before results were seen (core intake), it is the only trial (PSR); the neighbourhood is robustness only.

## 4. Statistics
- Returns = daily P&L of the marked curve (TradeBlocks daily log) divided by the fixed capital basis; non-trading days as flat days. State the frequency of every statistic.
- **ml4t-diagnostic** on these returns: PSR (uses skew and kurtosis - essential for short-premium strategies), MinTRL, block-bootstrap confidence intervals. **The multiple-testing hurdles (DSR over compared variants, vendor-trials sensitivity with the expected max Sharpe) run on the EXCESS return over the naive baseline, never on raw returns:** every cell of a short-premium grid earns the premium, so a raw-return DSR against Sharpe 0 passes an overfit winner (calibration: p = 0,028 at 35 trials, p = 0,042 at 100) while the excess-return test rejects it (p = 0,53 at 35 trials). The raw PSR only answers "does the structure earn premium at all".
- **Strategies that trade on fewer days than the baseline** (filters, skipped days): the daily excess return on a fixed capital basis is diluted by cash days and is biased against them; use the paired test on jointly held days (next bullet) as the primary comparison and report the raw excess only as context.
- **Paired test against the naive baseline**: both tapes in one TradeBlocks block with distinct strategy labels -> `paired_bootstrap_comparison`; report joint and arm-only days (SQL as in `is-this-optimum-real`, step 5). This is the options form of the core's paired benchmark test. To put two verified captures into one block when the capture tool's own combine refuses them (it accepts only run-bound captures), concatenate the two verified trade logs with distinct strategy labels, import trade-only (no daily log), and reconcile count and P&L per label with `run_sql` to the cent before testing. **Check the result:** the point estimate must lie inside its own interval and the interval must move sensibly across the reported `sensitivity` block lengths; in TradeBlocks 4.6.1 it did not (calibration: point 17,97 with interval [-19,37; 8,05], a recomputed paired day-block bootstrap gives [1,21; 35,59]). If the check fails, recompute the paired day-block bootstrap with own code (same attribution: P&L spread evenly over the days a trade is open, joint days only, same block length) and report both, flagging the tool result as unreliable.
- **Per-trade figures** from `get_statistics`: win rate, average win and loss, payoff ratio, largest loss in multiples of the average win (short-premium strategies: high win rate with rare large losses is the normal pattern, so the largest-loss multiple and the tail figures below matter more than the win rate). No 3:1 target share for options.
- **Explained by the premium?** (core section 8, path 3): if the strategy does not beat the naive baseline in the paired test, its return is the volatility risk premium of that structure - trading the naive version (or an option-writing index product) is cheaper and transparent.

## 5. Robustness and risk with TradeBlocks
- `portfolio_health_check` / `get_statistics` (marked-curve Sharpe, Sortino, Calmar, MAR, max drawdown, time in drawdown).
- `analyze_edge_decay`, `run_walk_forward`, `analyze_walk_forward_degradation`, `analyze_rolling_metrics`, `analyze_period_metrics`.
- `run_monte_carlo` (resample daily) for 1-year return and drawdown quantiles.
- **Tail and stress**: `get_tail_risk`, `stress_test`, `drawdown_attribution`, `analyze_regime_performance` / `analyze_regime_comparison` with `compute_vix_context`. **Stress-period rule:** if the record (or its verifiable out-of-sample part) contains no stress period with a volatility spike (e.g. Feb 2018, Mar 2020, Aug 2024, Apr 2025) and the replication cannot cover one either, the evidence grade is at most **B** whatever the other tests say; state the worst replicated stress day in multiples of the average daily P&L.
- `decompose_greeks` / `get_greeks_attribution` where the data supports it (is the P&L theta, short vega, or directional delta?).
- **Portfolio fit**: if the user runs an options portfolio, `get_correlation_matrix`, `marginal_contribution` and `what_if_scaling` against it (on the same capital basis); a real but redundant strategy may still not be worth adding.

## 7. Calibration
Re-run after every substantive change to this adapter. Two synthetic cases must both be rejected (no "tradable", no grade A even if the record type were `audited`):
1. **Overfit optimizer winner**: an Option Omega optimizer grid on an ordinary structure, take the best cell by the ranking metric as the "vendor record". Expected: `is-this-optimum-real` flags a spike or a boundary winner, the vendor-trials hurdle fails at the grid size, and the paired test vs. the plateau centre does not support the winner.
2. **Noise strategy**: a structure with entries chosen at random days/times (fixed seed), presented as a "vendor record". Expected: no significant edge over the naive baseline, PSR below the hurdle.
Record both runs, their verdicts and any rule that misfired in the user's run register / protocol; fix the adapter before the first real case.

Result of the first calibration (2026-11-08; SPX 7-DTE put credit spread, Mondays, 2016-01 to 2022-05, 35-cell grid delta 10-30 x stop 100-400 %):
- Overfit winner (delta 15 / stop 350 %, best of 35 by Sharpe): plateau rule flags a two-cell region next to cliffs, the broadest stable region lies elsewhere (delta 25-30 / stop 150-300 %), and the conclusion depends on the tolerance; paired test vs. the plateau centre not distinguishable from zero (excess Sharpe vs. centre -0,25); excess over the naive baseline PSR p = 0,22, at 35 trials p = 0,53; MinTRL of the excess 28 years. Rejected. **Misfire fixed:** the raw-return DSR passed it (now excess-only).
- Noise (base rule on a random half of the Mondays): paired difference vs. baseline on joint days 0,08 USD/day, interval around zero; raw PSR p = 0,20, MinTRL 25 years. Rejected. **Misfire fixed:** the daily excess on fixed capital was strongly negative only because of cash days (now paired test first).
- Tool finding: TradeBlocks `paired_bootstrap_comparison` interval inconsistent with its own point estimate in 2 of 3 comparisons (check added above).
